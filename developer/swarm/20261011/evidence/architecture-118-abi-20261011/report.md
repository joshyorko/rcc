## What Manifest v1 actually records

[Manifest fields, identity and validation](https://github.com/joshyorko/rcc/blob/324524fffa4bd0f76c618f9fbb6ede30e733b2ff/environmentartifact/manifest.go#L49-L89) include platform, generic builder kind/version/compatibility key, exact legacy blueprint/catalog/object-index descriptors, and `requirements.compatibility`. Compatibility is identity-bearing through `IdentityBytes` lines132–138. Changing a requirement creates a new Artifact identity; URLs, homes and trust carriers remain separate.

[Compatibility schema](https://github.com/joshyorko/rcc/blob/324524fffa4bd0f76c618f9fbb6ede30e733b2ff/environmentartifact/compatibility.go#L11-L50) records:

- Python implementation, exact version, ABI;
- OS family, minimum product/kernel version, libc family/minimum, architecture, translation policy, runtime and required library names;
- CPU architecture and sorted required feature names;
- filesystem case sensitivity, symlinks, junctions, long paths and minimum path bound;
- relocation version and whether build system requirements were overridden.

It does not record a per-extension Python ABI inventory, native library symbol/version map, package-specific CPU feature provenance, physical versus process architecture as separate fields, or a materialized-interpreter observation in the compatibility receipt. Existing exact object identities protect content bytes; they do not by themselves prove every native package can load on B.

[Builder collection](https://github.com/joshyorko/rcc/blob/324524fffa4bd0f76c618f9fbb6ede30e733b2ff/environmentlifecycle/builder.go#L20-L25) restores the producer environment to collect requirements. Lines64–85 use builder kind `rcc-holotree-v12` for this path and include compatibility in semantic specification bytes. A UV build is therefore established by its blueprint/build logs and resolved inventory, not a distinct `uv-native` builder label assumed from the Manifest.

## OS, CPU and filesystem claims needing qualification

The [platform contract](https://github.com/joshyorko/rcc/blob/324524fffa4bd0f76c618f9fbb6ede30e733b2ff/environmentartifact/platform.go#L8-L36) supports Linux amd64, macOS amd64/arm64, Windows amd64 and requires exact process `runtime.GOOS/GOARCH` plus RCC platform. Linux arm64 is not a missing unconditional matrix row in this contract.

Linux producer inspection scans ELF imported library names and `GLIBC_*` strings, removes any basename found bundled, and records the maximum discovered glibc version; if none is found it falls back to producer glibc. The OS family version is1 and kernel floor3.15. Worker libraries come from `ldconfig -p`, libc from `getconf`, CPU flags from `/proc/cpuinfo` (`compatibility_linux.go:20–98,114–150`). This is meaningful preflight but not full loader resolution, indirect `dlopen`, C++ symbol ABI validation or executable native instruction proof. Flags are accumulated across `/proc/cpuinfo` entries; no per-core intersection is calculated. That is a static limitation to qualify on heterogeneous hosts, not a runtime defect reproduced here.

Linux/Windows amd64 producers record only `sse2`; Darwin producers record no extra feature (`compatibility_linux.go:46–54`, `compatibility_windows.go:33–41`, `compatibility_darwin.go:33–37`). Windows worker feature collection also exposes only `sse2`; Darwin exposes an empty list. A simple new AVX2-positive fixture cannot succeed through current advertised Windows/Darwin capability collection without an implementation slice. Actual native instruction requirements are not inferred by these producers. The existing exact-binary CPU-negative receipt is a recomputed Manifest with `rcc-real-acceptance-impossible-feature` (`real_vertical_test.go:910–913`), proving generic early rejection rather than package-specific correctness.

Darwin records producer OS/kernel minima and probes `sysctl.proc_translated`. Its `NativeArchitecture` and CPU architecture are **RCC process GOARCH**, even when translated, not a separate physical Apple Silicon identity (`compatibility_darwin.go:16–37,83–106`). The matching amd64 artifact + translated amd64 RCC case can therefore reach translation policy evaluation. An arm64 RCC selecting an amd64 artifact is rejected by exact platform equality even with `translation-allowed`; that flag does not select or launch an emulator.

Darwin required non-system absolute library names are checked with `os.Stat`; `/usr/lib` and `/System` names rely on OS minima. Windows scans PE imports and checks library presence through host PATH/System32 (`compatibility_windows.go:44–105`). These presence checks do not prove symbol or extension ABI compatibility. The separate Darwin RPATH test transports real compiled dylibs, but supplies Python through a host shell wrapper and a recording builder (`rpath_lifecycle_darwin_test.go:54–110`): useful relocation proof, not a complete RCC-built Python/package A→B proof.

Filesystem requirement inventory detects actual case collisions/symlink entries and longest relative path, adds a fixed120-character allowance, and always sets `Junctions=false` (`compatibility.go:98–133`). Host capability tests create temporary probes (`218–258`); they cannot demonstrate an artifact-contained junction survived transport. The exact native fixture's platform program likewise creates links/long paths/junctions on B **after** acquisition (`real_vertical_test.go:811–874`). v12 catalogs have file/directory `symlink` fields (`htfs/directory.go:66–82`); whether each proposed safe link/junction is preserved, flattened or rejected must be asserted from catalog plus B bytes/targets, not assumed from those fields.

## Real package CPU and Rosetta receipts

Package CPU proof requires **both an actual requirement source and a matched positive/negative host**. A bounded reproducible option is a pinned tiny native extension/package compiled with an explicit AVX2 operation, fixed compiler/flags and binary hash, accompanied by a reviewed package CPU requirement declaration. The producer must actually emit `avx2` from that authoritative declaration/inventory; merely mutating a baseline Manifest is a separate predicate test. Run a positive host where the CPU and OS execution state support AVX2, execute the instruction through RCC after transport, then run the same immutable artifact on a dedicated CPU-masked VM/physical host without AVX2: nonzero `cpu-feature` rejection, zero object GETs, no Python probe/user marker/ready materialization. Preserve host CPU/OS evidence and provider counters. Current Windows/Darwin feature collection and requirement derivation need bounded implementation before claiming such a row; choose feature spelling/OS-state semantics once and test them. This report selects no package tier or new public override syntax.

Real Rosetta proof needs Apple Silicon hardware with Rosetta2 actually available and the **amd64 RCC binary run as amd64**. Retain physical host identity separately from RCC GOARCH, `sysctl.proc_translated` evidence from RCC's observed worker and the executed artifact Python, source/binary hashes and resolved amd64 native package bytes. Use a real amd64 artifact built on a compatible producer. With `native-only`, translated B must reject before object GETs. With a separately rebuilt, correctly identified `translation-allowed` artifact, translated B must cold-acquire, execute native SQLite plus the pinned extension, release a lease, then pass warm provider-dead and archive execution with unchanged trust inputs. Native arm64 and native Intel controls stay separate. A `translation-allowed` acquire on a native host or `skipped:native-runner` is not this proof (`real_vertical_test.go:433–442,879–898`). Provisioning/access to that host is an operator input; how to obtain truthful receipts is routine implementation/testing once it exists.
