## Source finding

The overlay gives each child a distinct process group (`Setpgid`), makes the Go process a Linux child subreaper, and its `close()` uses `Wait4(-group)` plus group-member census so concurrent supervisors should reap only their own group's adopted children. `Lease()` and `Release()` use the per-artifact process mutex and cross-process lock; each execution receives a distinct lease ID, and releasing A should not remove B's lease. Those are the right seams for an overlap control, but concurrent `ExecuteWithStreams` has not been established by the prior serial controls.

There is a fail-open lease-release path that must be addressed before relying on the overlay as a safety barrier. `executeWithSignalsAndStreamsInDirectory` registers the lease-release defer before the supervisor-close defer. On return, `supervisor.close()` runs first, but it only assigns its error when the named `err` is nil. During context cancellation, the return has already set `err = ctx.Err()`, so a close/census/reap failure is suppressed. The earlier lease-release defer then runs unconditionally and releases the lease; its own release error is also suppressed while `err` is non-nil. Thus `ExecuteWithStreams` can report ordinary cancellation and remove A's lease even if the overlay failed to prove A's descendants gone. Keep the lease active (or otherwise prevent reclamation) unless group drain has succeeded, and combine/report close failures with cancellation. This belongs in the private overlay/harness admission path; no production edit is authorized here.

The overlay's subreaper setting is process-wide and persists for the Go process. `Wait4(-group)` is group-specific, which should prevent A from stealing B's statuses, but only an actual concurrent test can establish that interactions, reparenting and status waits behave as intended. The supervisor is cooperative Linux process-group containment only; `setsid` escape, hostile tasks, long-lived pools and other platforms remain outside scope.

## Required isolated control

Use one fresh private `ROBOCORP_HOME`, one normal public `Acquire` of the exact retained artifact, and the same immutable materialization for both concurrent calls. Do not replay any timed workload. Run two short cooperative children through public `ExecuteWithStreams` from one Go process and one materializer, each with separate streams, context, execution group, and pipe protocol. Each child must emit a readiness row containing its own PID/start tick, grandchild PID/start tick, PGID, artifact digest, lease ID and process-start identity. Require distinct A/B groups and distinct lease IDs bound to the same artifact/owner.

After both readiness rows are parsed, verify both parent/grandchild identities are live, exactly those two lease records exist, and each lease's canonical contents match its handle. Snapshot B's lease bytes and file identity. Cancel A only after B is ready. A's `ExecuteWithStreams` must not return until the bounded group drain finishes. While B remains blocked and after A returns, require A's parent and grandchild identities absent, A's lease absent, exactly B's lease present and byte-for-byte unchanged, and both B identities still live. Send B a post-A-cancellation request and require a correct response bound to B's original PID/group/lease; then close B input, require clean EOF/exit, both B identities absent, and zero lease records. Use bounded per-phase deadlines and incremental receipts; any close/reap error, lease overlap/change, missing response, identity ambiguity, timeout, stray process or cleanup failure is a first-failure NO-GO. Retain evidence and stop without retrying an accepted control.

Before admitting that control, independently review the exact private overlay/worker/controller binding and prove: two distinct groups are created; cancellation targets only A; group drain errors cannot be hidden by `context.Canceled`; no lease is released before successful drain; A and B lease snapshots are cross-bound to their respective handles; stdout readiness parsing is complete-line and bounded; both descendants are census-checked by PID/start; child exit/reaping and home/task guards are strict; all resources are bounded. Following a successful control, a separate admission may authorize only this untimed overlap test. It does not authorize timed measurements, production changes, hostile/concurrent task isolation claims, persistent workers, macOS/Windows, or release/Actions qualification.
